Por onde começar

Esta página é executada, não lida. Colar a página inteira num agente instala globais que já lá estão e liga servidores com credenciais que o projeto nunca vai usar. Cola só a secção que corresponde ao que estás a fazer: A numa máquina nova, B num projeto novo, C quando precisares de uma ferramenta concreta. Na secção C a regra é liga, usa, desliga.
Há aqui git clone seguido de instaladores de terceiros, MCPs com credenciais e variáveis de ambiente com chaves. Cada bloco executável tem, por cima, uma linha a dizer o que faz à máquina — lê-a antes de correr. Se um repositório ligado mudar de conteúdo, o agente executa a versão nova sem ninguém rever.

Se só tiveres 10 minutos numa máquina nova, fica-te por estas 7, por ordem de impacto. O resto fica para quando precisares.

A · Uma vez por máquina

Instala-se uma vez e fica. Se estás num projeto novo numa máquina que já usas, salta esta secção inteira e vai directo à B.

Verificar o que já tens

Corre num terminal. Cada linha deve devolver uma versão.

Não altera nada — só lê versões.

# Node.js 20+ (necessário para servidores MCP e para o npx)
node --version
npm --version

# Claude Code CLI — 2.1.170+ para o alias `fable` nos subagentes
claude --version

# o npx tem de correr: é ele que arranca metade dos MCPs
npx --yes skills@latest --version
Falta o Claude Code? Instala com npm install -g @anthropic-ai/claude-code e autentica com claude (segue o login no browser). Se a versão for inferior a 2.1.170, corre claude update antes de criar os subagentes.
Se o último comando falhar com Class extends value undefined is not a constructor or null, o problema é o Node, não o pacote — vê Problemas comuns. Acontece com o nvm do Herd, e parte também o Chrome DevTools MCP e tudo o resto que arranque por npx.

Orquestração de modelos obrigatório

Configura o Claude Code para delegar a subagentes com o modelo certo para cada tipo de tarefa. Delegar bem reduz custo e melhora a qualidade; delegar por sistema faz o contrário.

Ou instala de uma vez. Escreve os quatro agentes e o bloco do CLAUDE.md a partir do perfil escolhido. Corre --dry-run primeiro: lista o que altera e o que não altera, sem escrever nada.

curl -fsSL https://skills.criativatek.com/install/profile.sh | bash -s -- --profile standard --dry-run
Tira o --dry-run para instalar. Guarda os agentes anteriores em ~/.claude/agents/.bak-<data>/ e substitui só o bloco entre marcadores do CLAUDE.md — se já lá tens a secção ## Orquestração de modelos sem marcadores, migra-a em vez de deixar duas políticas contraditórias no mesmo ficheiro. --rollback volta ao perfil anterior sem rede. Windows: Git Bash, como os outros blocos.
O que se esquece: no contexto principal o que pesa é sobretudo o relatório devolvido — e esse é relido em todos os turnos seguintes. Um relatório de 8k no turno 10 é pago outra vez em cada um dos 90 turnos que se seguem. Por isso cada agente abaixo tem um orçamento de saída escrito na definição.

Quem recebe o pedido primeiro

Não há roteador antes do modelo principal. O pedido entra na sessão, e é o modelo principal que decide se delega, a quem, e o que faz com o que volta.

Pedido
  ↓
Modelo principal da sessão — coordenador (Opus em trabalho complexo, Sonnet no dia a dia)
  ├── explorer     · Haiku  · levantamento de contexto
  ├── implementer  · Sonnet · trabalho paralelo ou mecânico
  ├── architect    · Fable  · decisões difíceis de reverter
  └── reviewer     · Opus   · revisão independente

O coordenador faz o juízo mais difícil da cadeia — decidir se vale a pena delegar — e delegar mal custa mais do que não delegar. Com um principal em Sonnet, o implementer continua a valer pelo isolamento de contexto: uma tarefa secundária que inundaria a conversa principal corre à parte e devolve só o essencial. O que não compensa é chamá-lo para a tarefa seguinte de um trabalho já em curso — aí reexplicar o contexto custa mais do que se poupa.

O Fable está no architect, não no reviewer. No Max, o Fable conta para o mesmo balde de utilização, limitado a 50% do limite semanal — é um tecto dentro do plano, não utilização adicional. Isso torna decisivo qual agente o usa: o architect dispara menos vezes e nas situações de maior consequência. O reviewer é chamado muito mais vezes, e a maior parte delas em alterações banais — em Fable, gastava metade do plano a rever formulários e CSS. Metade do limite semanal está incluída: não a gastar também é desperdício, mas gasta-se onde a decisão é difícil de reverter, não onde é só trabalho.

    CLAUDE.md global obrigatório

    A tabela de subagentes não chega: é preciso dizer ao modelo principal quando delegar. Este bloco delega por excepção.

Duas instruções contraditórias no mesmo ficheiro dão comportamento não determinístico — e não controlas qual delas ganha. 

    ## Orquestração de modelos

Trabalha autonomamente até o objetivo estar concluído. Delega aos subagentes de
`~/.claude/agents/` **por excepção**, não por sistema.

Ao delegar, a execução do subagente conta para a utilização total; no contexto
principal pesa sobretudo o relatório devolvido, que é relido em todos os turnos
seguintes. Antes de chamar um subagente, pergunta "de que tamanho tem de ser a
resposta para eu decidir?" e diz-lhe esse tamanho.

| Subagente | Modelo | Quando |
|---|---|---|
| `explorer` | Haiku | Levantamento amplo de contexto. Para uma pergunta pontual, faz o Grep tu — um subagente devolve sempre mais do que um Grep. |
| `implementer` | Sonnet | Duas ou mais tarefas independentes em paralelo, ou trabalho mecânico em muitos ficheiros. Não para a tarefa seguinte de um trabalho em curso. |
| `architect` | Fable | Decisões estruturais, alterações entre módulos, migrações, erro de causa não óbvia. É o agente mais caro — reserva-o para o que é difícil de reverter. Só analisa. |
| `reviewer` | Opus | Sessão longa, alteração grande, ou código que fecha sem mais ninguém ver. Não a cada commit. Só analisa. |

Em zonas sensíveis — autenticação, pagamentos, dados pessoais, migrações, lançamento
em produção — pede uma segunda passagem independente em vez de aceitar a primeira
revisão. Essa escolha é minha, não tua: não a faças automaticamente.

## Regras de trabalho

- Diagnostica antes de ler. Uma query, um `grep -c`, um `artisan route:list | grep`
  devolvem a resposta; ler o ficheiro devolve o material de onde se extrai a resposta.
- `Read` com `offset`/`limit` quando já sabes onde está a resposta. Ficheiro inteiro
  só quando é mesmo preciso.
- Verifica contra dados reais antes de escrever código que dependa deles.
- Planos curtos: o plano é pago ao escrever e outra vez ao aprovar.
- Não peças confirmação para decisões técnicas reversíveis.
- Corre testes, lint e análise estática antes de dar uma tarefa por concluída.

## Documentação

Documenta o que não se lê no código: decisões e o porquê, o que foge à convenção,
armadilhas descobertas à força, acessos que não se adivinham.
Não documentes o que o código já diz — o que cada método faz, a estrutura de pastas,
listas de rotas ou modelos.
Antes de fechar uma tarefa não-trivial, pergunta o que foi preciso descobrir que não
estava escrito em lado nenhum, e escreve só isso.
Mantém o CLAUDE.md do projeto dentro de um ecrã: é relido em todos os turnos de todas
as sessões.

    Higiene de sessão recomendado

    O custo cresce com contexto carregado × número de turnos: tudo o que entra no turno 10 é pago outra vez em cada turno seguinte. Quatro sessões de 25 turnos custam uma fracção de uma de 100 — e o modelo responde melhor num contexto limpo.

    Nada a instalar. É um hábito, mais um ficheiro de notas por tarefa.

    Não existe /clear automático. O que é automático é a auto-compactação, que resume a conversa quando o contexto enche — isso não é limpar, é comprimir com perda, e é precisamente o momento em que a qualidade cai. Os hooks de sessão reagem a um /clear, mas nenhum o provoca.
    PráticaPara quê
    Notas de tarefa em cursoAntes de limpar, um ficheiro curto com o estado: onde estou, o que já verifiquei, o que falta. Não é documentação do projeto — é memória de tarefa.
    claude -p "…"Tarefas isoladas e scripts: corre e sai, contexto novo garantido.
    Hook de sessãoRepõe o estado automaticamente no arranque, para que limpar não custe nada. É configuração por projeto — ver secção B.

    Context7 recomendado único MCP a escopo de utilizador

    Injeta documentação atualizada de qualquer biblioteca (Tailwind, Vue, React, Laravel, Node…) diretamente no contexto. Acaba com respostas baseadas em versões antigas. É o único servidor que se instala uma vez por máquina — o Motion também entra em todos os projetos, mas a -s project, com o resto da secção B.

    Regista um servidor MCP remoto em user scope — fica activo em todos os projetos.

    claude mcp add --transport http context7 https://mcp.context7.com/mcp -s user
    O contexto já não é o argumento principal para restringir MCPs. A tool search está activa por defeito: no arranque só carregam os nomes das ferramentas e as instruções do servidor, e os esquemas completos entram só quando são precisos. Acrescentar servidores tem hoje impacto pequeno na janela — muita literatura sobre o assunto ainda descreve o comportamento antigo.
    As razões para restringir mantêm-se, mas são outras: credenciais — um MCP com acesso à BD ou ao GitHub ligado em todos os projetos é acesso que não precisas de ter aberto; precisão da escolha — acima de umas dezenas de ferramentas disponíveis o agente escolhe pior entre alternativas parecidas; relevância — instruções de servidores irrelevantes continuam a carregar no arranque e a competir pela atenção do modelo.

    Skills globais recomendado

    De cada skill instalada fica sempre carregado o nome e a descrição — é assim que o agente sabe que existe. O corpo só entra quando é invocada, e aí fica até ao fim da sessão. Global só para o que é transversal a quase todos os projetos: sete aqui, mais a Task Observer a seguir — oito ao todo. Stack, Playwright, design e marketing instalam-se por projeto.

    Escreve pastas em ~/.claude/skills/ e regista-as em ~/.claude/skills-lock.json. Código de terceiros que corre com as permissões do agente.

npx skills add https://github.com/github/awesome-copilot --skill refactor -g
npx skills add https://github.com/vercel-labs/skills --skill find-skills -g
npx skills add https://github.com/obra/superpowers --skill systematic-debugging -g
npx skills add https://github.com/obra/superpowers --skill writing-plans -g
npx skills add https://github.com/obra/superpowers --skill executing-plans -g
npx skills add https://github.com/obra/superpowers --skill verification-before-completion -g

    Task Observer obrigatório

    Observa a sessão em curso e regista o que aprendeste à força — correcções que deste ao agente, padrões de trabalho, decisões que se repetem. Escreve num log estruturado e, num ciclo de revisão separado, transforma esse log em skills novas ou melhoradas. Não altera skills sozinha: propõe, tu decides.

    Escreve .agents/skills/task-observer/ com link simbólico para o Claude Code, e um log em skill-observations/.

    npx skills add https://github.com/rebelytics/one-skill-to-rule-them-all --skill task-observer -g
    MomentoO que fazer
    Durante a sessãoNada — observa sozinha depois de invocada
    Ao fecharPerguntar «alguma observação registada?» antes do commit
    Ciclo de revisãoLer skill-observations/log.md e decidir o que vira skill
    Custa ~7k tokens em todos os turnos. O SKILL.md tem 24,9 KB e a skill foi feita para estar activa a sessão inteira — pela regra das skills globais, o corpo entra quando é invocada e fica até ao fim. Numa sessão longa isso é mais caro que qualquer outra skill deste guia (a motion, para comparar, tem 4,5 KB e só carrega quando animas). Se a sessão for curta ou mecânica, não a invoques.
    Sobrepõe-se a três coisas que já tens. A learn guarda aprendizagens do projeto, o GBrain dá memória persistente pesquisável, e a regra de memória do CLAUDE.md global já manda guardar decisões e armadilhas antes de cada commit. O que esta acrescenta é fazê-lo sem lhe pedires — e é essa a parte a vigiar, porque cada skill que ela propuser passa a custar nome e descrição em todas as sessões seguintes. Aceita poucas.

    gstack recomendado instalação diferente

    Suite grande de skills para todo o ciclo de engenharia com IA — browser headless rápido (/browse), revisão de planos por perfis (CEO, design, eng, devex), ship/deploy (/ship, /land-and-deploy, /canary), debugging sistemático (/investigate), pentesting autónomo (/shannon) e memória persistente local (/setup-gbrain). Um repositório, um instalador.

    Clona um repositório de terceiros para ~/.claude/skills/gstack e corre o instalador dele. Instala ~55 skills de uma vez. Lê o setup antes de correr.

    git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack
cd ~/.claude/skills/gstack && ./setup
    Sobrepõe-se ao Playwright e ao Chrome DevTools para tarefas de browser — usa o gstack para QA/dogfooding rápido do dia a dia, e o Playwright quando precisas de testes E2E formais. A /investigate do gstack sobrepõe-se à systematic-debugging: escolhe uma e habitua-te a ela.

    GBrain recomendado

    Memória persistente local (RAG) entre sessões e projetos — o Claude deixa de precisar de reexplicar contexto ou reler o código todo em cada conversa nova. Pesquisa semântica sobre código e notas via gbrain search / gbrain code-def, registada como MCP. Requer o gstack.

    Cria uma base de dados local em ~/.gbrain/ e regista um MCP em user scope.

    /setup-gbrain
    Escolhe PGLite local para uso a solo (sem contas, ~30s, cérebro isolado nesta máquina). Supabase/remoto só compensam para partilhar a memória entre máquinas ou com a equipa. Chave de embeddings antes de correr: VOYAGE_API_KEY (recomendada para código), ou OPENAI_API_KEY. Sem chave o assistente deixa avançar (--no-embedding) mas fica sem pesquisa semântica.
    gbrain ✗ Failed to connect em Windows quase sempre é um processo gbrain serve órfão a segurar o lock do PGLite — mata-o e o servidor volta. Ver Problemas comuns.

    CodeBurn recomendado

    Dashboard local (terminal) que lê os logs de sessão e mostra custo/tokens gastos por projeto, modelo e tarefa, em 31 ferramentas diferentes (Claude Code, Cursor, Codex, Gemini…). Corre 100% local — sem API key, nada sai da máquina. Complementa o /usage: aquele é do plano, este é por projeto/cliente.

    Não instala nada — npx corre e sai. Lê os logs de sessão locais.

    npx codeburn

    Caveman opcional

    Faz o Claude Code responder em estilo comprimido — sem artigos, sem palavras de preenchimento, telegráfico — mantendo código, paths e URLs intactos.

    Instala um plugin e um marketplace no Claude Code. Activa-se em todas as conversas, em todos os projetos.

    claude plugin marketplace add JuliusBrussee/caveman
claude plugin install caveman@caveman

    Hook de sessão recomendado

    Este hook automatiza o custo de limpar, não o limpar: injecta contexto fresco no arranque de cada sessão — o stdout do hook entra directamente no contexto do agente — para que /clear não custe nada.

    Corre comandos de shell no arranque de todas as sessões deste projeto, e o output entra no contexto.

    {
  "hooks": {
    "SessionStart": [
      {
        "matcher": "startup|clear",
        "hooks": [
          {
            "type": "command",
            "command": "git branch --show-current && git status --short && cat .claude/session-context.md 2>/dev/null"
          }
        ]
      }
    ]
  }
}
    Põe isto no settings.json do projeto, nunca no global. O stdout do hook entra directamente no contexto principal: um hook global que faz cat a um ficheiro do repositório deixa qualquer projeto — incluindo código de cliente ou uma dependência clonada — injectar conteúdo à escolha na tua sessão. Ficheiro com nome controlado (.claude/session-context.md), e só em projetos em que confias. Mantém o hook rápido: corre em todas as sessões.

    Escreve CLAUDE.md na raiz do projeto — relido em todos os turnos de todas as sessões.

    Como medir

    Duas ferramentas, duas perguntas diferentes.

    ComandoResponde a
    /usageO que já gastaste. Barras do plano com a repartição por skills, subagentes, plugins e servidores MCP. d / w alterna entre 24 horas e 7 dias.
    /context allO que está a ocupar a janela agora. É aqui que se vê, sem teorizar, o que cada MCP, skill e ficheiro está mesmo a custar nesta sessão.
    Tira uma leitura de uma semana normal antes de aplicar seja o que for. Sem baseline, daqui a duas semanas não se sabe se melhorou ou se só mudou o sítio onde se gasta. Corre os dois comandos numa sessão de trabalho real, não numa sessão vazia — uma sessão vazia mede o arranque, não o uso.

    Dois números a vigiar depois:

    1. Volume devolvido por chamada a Agent

      Agregando os .jsonl em ~/.claude/projects/. Com os orçamentos aplicados, a mediana deve aproximar-se de 1k tokens — mas o número que interessa é o máximo: é a cauda de relatórios gigantes que faz o estrago, não a mediana.

      $logs = Get-ChildItem "$env:USERPROFILE\.claude\projects" -Recurse -Filter *.jsonl |
        Sort-Object LastWriteTime -Desc | Select-Object -First 150
$sizes = @()
foreach ($log in $logs) {
  foreach ($line in [System.IO.File]::ReadLines($log.FullName)) {
    if ($line -notlike '*"toolUseResult"*') { continue }
    try { $entry = $line | ConvertFrom-Json } catch { continue }
    if ($null -eq $entry.toolUseResult) { continue }
    $json = $entry.toolUseResult | ConvertTo-Json -Depth 8 -Compress
    if ($json -notlike '*subagent*' -and $entry.message.content.name -ne 'Task') { continue }
    $sizes += $json.Length
  }
}
$sorted = $sizes | Sort-Object

    Problemas comuns

    SintomaCausa e solução
    npx, npm install -g ou claude update falham com Class extends value undefined is not a constructor or null Não é a cache nem o pacote: é uma árvore do Node incoerente. Acontece com o nvm do Herd quando uma pasta de versão (ex.: nvm\v20.20.2) foi sobreposta por binários de outra major — o node.exe lá dentro não é da versão que o nome diz, e o minizlib do npm rebenta no require.

    Parte toda a camada de rede do npm, não só o npx: npm view, npm install -g, claude update e todos os MCP que arrancam por npx (Chrome DevTools, Playwright, MySQL). Só os comandos offline (npm --version, npm run build) continuam a passar — o que faz parecer que o npm está bom.

    Diagnosticar: & "$env:USERPROFILE\.config\herd\bin\nvm\v20.20.2\node.exe" --version — se não devolver 20.x, é isto.
    Corrigir: nvm use 22.23.1 (ou outra versão íntegra). Reversível com nvm use da anterior.
    Mudei de versão com nvm use e o claude desapareceu do PATH No nvm-windows os pacotes globais do npm são por versão: cada nvm\vX.Y.Z\ tem o seu node_modules. Trocar de versão órfã todos os globais de uma vez — claude, codex, gemini, codeburn. Não se perdem, deixam de estar no PATH.

    Lista o que ficou para trás e reinstala na versão nova: Get-ChildItem "$env:USERPROFILE\.config\herd\bin\nvm\v<antiga>\node_modules" -Directory e depois npm install -g <pacotes>. Aproveita para actualizar — é a mesma operação.

    Alterei um ficheiro em ~/.claude/agents/ e nada mudou São carregados no arranque da sessão. Reinicia. Só as alterações feitas pela interface /agents entram de imediato. O mesmo vale para o CLAUDE.md.
